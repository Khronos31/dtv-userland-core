# Receiver v1 ストリームライフサイクル

`dtv::receiver` は、従来のストリーム契約入口と v1 契約入口を別個の独立した動作モードとして維持する。v1 を利用する場合は、初回の ACQUIRE 呼び出しより前に v1 構成を設定しなければならない。選局処理（tune）が成功すると最新の選局リビジョン（tune revision）が公開される。後続の START 要求は必ずそのリビジョン番号を指定して呼び出さなければならず、有限の準備期限（arm deadline）を伴う新しいストリーム ID およびアタッチ用トークンが返却される。

データワーカーは厳密な START の識別情報を確保した上で、まず `prepare_attach_v1()` を呼び出してキャプチャ処理を開始しデータプレーンの接続準備を行う。そして、アタッチメントがアクティブ状態となったことを確認した後にのみ `commit_attach_v1()` を呼び出す。サービス側は、この確定コミットが成功した後に初めてストリームの正式受諾をクライアントへ応答（acknowledge）する。処理中断（abort）および STOP 要求は、該当ストリームの終端結果（terminal result）を保持し、物理クリーンアップの実行責任を高々 1 つの所有者へ引き渡す。返却された STOP 結果内の `cleanup_owner` フラグは、このクリーンアップ責任を引き受けた呼び出し側を識別する。終端結果レコードが得られたこと単体は、ハードウェアの動作が物理的に静定（quiesced）したことを意味しない。

`cleanup_owner` が true の場合、割り当てられたワーカーは該当の選局チケットを伴って `run_stream_cleanup_v1()` を実行する。本処理は prepare 処理に対して直列化され、レシーバミューテックスの取得後に物理キャプチャおよびデータアタッチメントの所有権を再確認した上で、必要な停止およびデタッチ処理を実行し、ハードウェアの静定状態を記録する。これに対し、`complete_stream_cleanup_v1()` は、他の実行経路において既に物理的なクリーンアップが実施・検証されている呼び出し側のための、メタデータ専用の完了通知パスである。自らキャプチャ停止やセッションデタッチを行うことはない。その `quiesced` 引数は呼び出し側自身の観測結果を記録するためのものであり、実際の物理クリーンアップが完全に完了する前に true を設定してはならない。

レシーバエンジンは、厳密な Hz 単位での正確な選局検証を行うために `TuneReadiness` を採用している。従来の kHz 単位による選局処理は引き続きロック状態のポーリングを継続する。`terminal_lock` はバックエンドから正当な正のロック検出測定値が得られることを要求し、`commands` はコマンド送信のみの検証結果を記録し、`ts_sync` はバックエンドにおける TS 同期結果を要求する。terminal-lock の観測サンプルが欠落している場合は選局エラーとして扱い、プログラミングコマンドの送信成功のみからロック成立を推定することは決してない。
