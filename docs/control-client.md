# 制御クライアント

`dtv::control` は、ソケット I/O を自前で持たないプロトコルゲートコンポーネントとして、状態照会 API（status API）、期限付き録画 API（recording API）、および独立 LNB 給電クライアントを提供する。呼び出し側が `ClientTransport` または `TimedClientTransport` を実装して注入する。本 Core ライブラリ自体はソケット生成やファイルディスクリプタ（FD）アダプターを提供しない。読み取り専用の `fetch_status` は HELLO、LIST、STATUS のみを要求し、ACQUIRE、TUNE、START、STOP、RELEASE などの状態変更操作は一切行わない。録画 API の `begin_recording`、`stop_recording`、`release_recording` は、それぞれ明示的にこれらの制御要求を発行する。

`fetch_status` は同一のトランスポート上で HELLO、筐体スコープの LIST、および STATUS を順に要求し、要求 ID に 1、2、3 を割り当てる。任意の追加機能（optional features）を要求せず、基本の UDTV 1.0 を指定する。HELLO で合意されたバージョン、同一系列内での epoch、プロデューサーの製品名/バージョン、正規 LIST レコード、および `validate_status_response` による LIST 基準での STATUS レコードを厳格に検証する。LIST と STATUS が公開する筐体および機能の identity フィールドの一致も照合する。Model は現行仕様に従い名前のみ（name-only）のフィールドで比較する。本関数を呼び出す前に、未使用の新規接続を渡さなければならない。

フレームおよび一時ペイロードの格納には、1 つの上限付きワークスペースを使用し、各応答処理でペイロード記憶領域を再利用する。このワークスペースは関数呼び出し中のみ有効な約 135 kB（約 132 KiB）のヒープ領域であり、制御ペイロード上限の要求フレームと応答ペイロードを独立して保持する（メモリ確保に例外機構は使用しない）。領域確保に失敗した場合は `RESOURCE_LIMIT` と既定の失敗結果を返し、トランスポートを即座に切断（close）する。デコードされたフレームビューは `FrameReceiver` の受信読み取りが進む前に処理を完了し、呼び出し元へ返却されるスナップショットやセッションオブジェクトは型付きレコードの所有権を持つため、トランスポートやワークスペースの内部バッファを参照し続けることはない。`ClientTransport` は呼び出し側の所有物であり、呼び出し中は常に有効でなければならない。`write_all` はビュー全体の書き込みを完了して成功するかエラーを返す。`read_some` は読み取ったバイト数、ストリーム終端を示す 0、またはエラーを返す。読み取り成功時にはフレームの断片や複数フレームの連結が含まれうるが、クライアントは要求に合致しないフレームを受け付けない。opcode および要求 ID が一致する response または error_response のみを処理対象とする。

スタック消費量は呼び出し側スレッドの実行環境に依存する。Linux x86_64 環境の Clang 19.1.7（Release ビルド）において、CMake の Release 既定値（`-O3 -DNDEBUG`）を `-O2 -DNDEBUG -fstack-usage` に置き換えて実測したところ、`fetch_status` のフレームが 64,888 バイト、共有 records デコーダの `decode_status_response` フレームが 54,248 バイト、返却される `StatusFetchResult` が 64,400 バイトであった。これらを単純合算すると 183,536 バイト（179.2 KiB、約 184 kB）となり、呼び出し側自身のスタックフレームやランタイムオーバーヘッドがこれに加算される。処理結果を呼び出しスレッドのローカル変数に配置する場合は、これらの合計スタック消費量を考慮する必要がある。小規模スタックのテストでは、結果構造体をプローブスレッド内に配置した正常系および EOF 経路について、最適化済み構成で 256/512/768 KiB、無最適化構成で 512/768 KiB のスタックサイズを用いて動作を確認している。256 KiB は最適化済み構成における参考実測値であり、すべてのビルド構成や呼び出し元に対する動作保証ではない。Clang 19.1.7 ではビルド種別未指定の無最適化構成において 256 KiB のプローブがスタックオーバーフローを起こしたため、当該構成では 512 KiB 以上での動作を確認している。GCC 14.2（Release ビルド）では CMake 既定の `-O3 -DNDEBUG` に `-fstack-usage` を追加して計測し、デコーダフレームが 108,464 バイト、`StatusFetchResult` を同一スレッドに配置する正常経路全体で約 237 KiB であった。GCC 14.2（Debug ビルド、ASan+UBSan 有効: `-g -fsanitize=address,undefined -fno-sanitize=vptr`）では、独立したプローブ計測において正常経路に約 295 KiB を要した。サニタイザランタイムや計装コードによるスタック消費増加はコンパイラおよびビルド構成に依存するため、通常ビルドのフレーム値から一律に換算することはできない。このため、サニタイザ有効時は小スタックテストのプローブを 512/768 KiB とし、通常ビルド時は最適化済みで 256/512/768 KiB、無最適化で 512/768 KiB として、早期 EOF 検出と正常系完了の双方を検証している。

ここで表記するプローブの単位 KiB は 1024 バイト、kB は 1000 バイトを表す。CMake の標準的な Release 既定は `-O3 -DNDEBUG`、Debug 既定は `-g` である。`dtv_userland_control` およびその依存ターゲットには `-fno-exceptions -fno-rtti -Wall -Wextra -Wpedantic` が付与される。前述の最適化およびサニタイザ用フラグは各測定で個別に使用した追加・置換設定であり、すべてのビルドへ一律に適用されるものではない。スタックプローブの検証は Linux x86_64 環境で実施された限定的な測定結果であり、あらゆる OS やコンパイラ環境でのスタック上限を保証するものではない。呼び出し側は結果オブジェクトの配置先やデコーダの消費量を考慮し、十分なスタックマージンを確保しなければならない。

通信失敗時は既定のスナップショットとローカルエラーを返す。リモート側からエラー応答を受信・デコードできた場合は、その生のエラーコード（raw code）も合わせて保持する。いずれの失敗時もトランスポートの `close()` を呼び出す。未知のリモートエラーコードを受信した場合は、生コードを保持したまま `PROTOCOL_ERROR` に対応づける。処理成功時はトランスポートを開いたまま呼び出し元へ復帰する。クライアント層による自動再試行は行わない。本 API 自体はタイムアウト値や再試行ポリシーを規定せず、ブロッキング待機および中断（cancel）の制御は注入されたトランスポート側の責務とする。

読み取り専用の `fetch_status` は ACQUIRE、TUNE、START、STOP、RELEASE などの状態変更を行わない。録画 API は ACQUIRE、TUNE、START、STOP、RELEASE の制御電文のみを扱い、上位サービス呼び出し、データ接続の ATTACH、TS_DATA の受信処理、ハードウェア操作、USB アクセス、製品個別機能の制御は行わない。UDTV wire プロトコルは、採用された層モデルにおいて外部契約（L2 規範）として位置付けられている。本クライアントはその wire 規範に準拠して動作する。ただし、リリースをまたぐ無期限の安定 C++ ABI を保証するものではなく、同一メジャー内での具体的な互換範囲は上位の外部契約規定に従う。

## 期限付き status/recording クライアント

制限時間を設けた操作には、拡張された `TimedClientTransport` を注入する。これは呼び出し側が所有権を持ち、`write_all`、`read_some`、`monotonic_ms`、`close` を実装する。既存の `ClientTransport` が持つ純粋仮想関数、および `fetch_status(ClientTransport&)` の関数シグネチャ・ブロッキング挙動はそのまま維持される。期限付きクライアントは同一のトランスポートオブジェクトを借用するのみであり、ソケットやファイルディスクリプタ（FD）を自前で生成・所有することはない。各読み書きの実装は渡された有限のタイムアウト期限を遵守し、期限超過後も処理をブロックし続けないことが前提となる。

`fetch_status(TimedClientTransport&, Timeout)` は、処理開始時にモノトニックタイマー（単調増加クロック）に基づく絶対期限（absolute deadline）を 1 つ算出し、HELLO、LIST、STATUS の各送受信および断片データの読み取りを通じて同一の残余時間を引き渡す。部分的な処理が進展しても期限が延長されることはない。制限時間値に 0 が指定された場合は `INVALID_ARGUMENT`、期限の算出値がタイマー（クロック）の uint64 表現範囲を超過した場合は `TIMEOUT` とし、いずれの場合もトランスポートを切断して既定の空スナップショットを返す。通信タイムアウト、EOF 検出、デコード失敗、検証不整合が発生した場合もトランスポートを閉じ、不完全なスナップショットは外部へ公開しない。成功時は有効なスナップショットを返し、接続は呼び出し側へ開いたまま返却する。

`fetch_status(TimedClientTransport&, Timeout, required_features)` は、同一の HELLO、LIST、STATUS シーケンスを単一の期限内で実行し、HELLO 電文で必須機能マスク（required feature mask）を送信する。要求された必須機能を提供しないサーバは HELLO 段階で接続を拒否する。サーバからの応答が要求マスクを満たさない場合も `UNSUPPORTED`、要求していない機能が暗黙に含まれているなど応答マスクが不整合な場合は `PROTOCOL_ERROR` とし、既定スナップショットを返してトランスポートを切断する。`required_features == 0` を渡した場合は、既存の期限付きオーバーロードと同様に状態取得のみのネゴシエーションとなる。非期限付き `ClientTransport` との互換性および既存の仮想関数形式は変更されない。

`begin_recording` は最初に内部で `fetch_status` を実行し、必要に応じて ACQUIRE より前に `RecordingStatusValidator` を呼び出す。バリデータにより開始不可と判定された場合は、既定のセッションオブジェクトを返し、トランスポートを切断する。状態取得フェーズの期限が完了した後、後続の ACQUIRE、TUNE、START フェーズに対して同一の長さを持つ新しい独立した期限を設定する。この「状態取得」と「選局・開始」という 2 つの独立したタイムアウト枠（2 budget）による制御は、旧来の録画ヘルパー実装との後方互換性を維持するための挙動であり、begin 処理全体を単一の制限時間枠に統合するものではない。各種オプションの数値既定値や許容範囲、`TuneRequest.timeout_ms` に対する各製品側の対応状況、OS ソケットのタイムアウト値との換算規則は本仕様では定義しない。

この 2 つの独立したタイムアウト枠（2 budget）の分割は、旧録画ヘルパーとの互換性を保つための現行実装上の選択であり、将来の製品向けタイムアウト契約や恒久的な利用規約を定めるものではない。新たなタイムアウト数値、既定値、製品オプションとの換算はここでは規定しない。

begin 処理は、1 つの上限付きワークスペースを例外非使用のヒープ確保によって使用し、既存の status 実装が持つ応答デコーダおよび検証処理を呼び出す。ACQUIRE、TUNE、START のいずれかの段階で処理が失敗した場合は、既定セッションとリモートの生エラーコードを返し、トランスポートを切断する。すべての開始処理が完全に成功した後にのみ、epoch、利用権（lease）、選局結果/リビジョン、stream ID、アタッチ用トークン、有効期限、次回 request ID を保持する呼び出し側所有のセッションオブジェクトを返す。アタッチ用トークンは別個に確立されるデータ接続での ATTACH にのみ使用されるものであり、本クライアントがデータソケットを生成したり ATTACH を実行することはない。START の成功はデーモン側で準備が完了（armed 受理）したことを示すのみであり、TS データがアクティブに流れていることを保証するものではない。

`stop_recording` はセッションが保持するストリームに対して型付き STOP 要求を 1 回送信し、受信機の利用権（lease）は解放しない。`release_recording` はセッションのリースに対して型付き RELEASE 要求を 1 回送信して利用権を返上する。両 API ともに応答不明や通信失敗となった要求の自動再送は行わず、成功時はトランスポートを開いたまま復帰する。タイムアウト発生時に、応答が届く前にデーモン側で START、STOP、RELEASE が実際に適用されたかをクライアント側から判定することはできないため、タイムアウト後に物理クリーンアップの完了やハードウェアの完全停止（quiesce: `quiesced=true`）を暗黙に推定してはならない。切断後のリソース回収はデーモン側の所有権契約が担うべき責務である。

## CARD セッションクライアント

`begin_card(TimedClientTransport&, CardClientOptions, Timeout)` は、CARD_SERVICE を必須機能として HELLO を行い、同一接続上で LIST、STATUS、リーダー存在確認、CARD_STATUS、CARD_CONNECT を順次実行する。HELLO/LIST/STATUS の一連の処理にひとつの制限時間を割り当て、CARD_STATUS/CARD_CONNECT にはその後に開始される同一の長さを持つ新たな制限時間枠を使用する（各フェーズ内で期限の延長は行わない）。要求 ID には 1〜5 を割り当てる。指定されたリーダーがスナップショット内に存在しない場合や、identity 制約が合致しない場合は、`NOT_FOUND` を返して接続を切断し、リーダーや CARD 機能の存在を推定しない。接続と初期化に成功した場合は、デーモンの epoch、リーダー ID、カードハンドル、世代番号（generation）、CARD_CONNECT により選択された通信プロトコル、次回 request ID（6）を `CardClientSession` に格納し、接続を開いたまま返却する。

`card_status` は、セッションが保持する epoch およびリーダー ID を用いて、現在の世代番号、カード挿入状態、初期化状態を取得する。`card_reset` は、セッションの epoch、リーダー ID、ハンドル、束縛世代番号を送信する。応答電文が同一の epoch、リーダー ID、ハンドルを示し、かつ型付きセッション結果の検証に成功した場合にのみ世代番号とプロトコルを更新し、ATR データを含む応答を返す。`card_transmit` は、利用可能（usable）なセッションに記録されたプロトコルと一致する T=1 プロトコル、および 1〜4096 バイトの APDU コマンドを受け付け、同一の epoch、リーダー ID、ハンドル、世代番号を持つ応答のみを外部へ公開する。TRANSMIT の応答データも最大 4096 バイトであり、応答キーの不一致やデコード失敗時は既定の空応答を返す。`card_disconnect` は、セッションの epoch、リーダー ID、ハンドル、束縛世代番号を送信する。応答が同一のリーダー ID およびハンドルを示し、かつ `consumed=true` であれば、ハードウェア停止（quiesced）の成否やクリーンアップエラーの有無にかかわらず、セッション内のハンドル、世代番号、プロトコル情報を無効化（消費）し、型付き応答結果を保持する。クリーンアップエラーが報告された場合はリモートのエラーコードを保持して対応する Error を返し、エラー報告がないにもかかわらず `quiesced=false`（停止処理未完了）である場合はプロトコルエラー（PROTOCOL_ERROR）とする。`consumed=false` かつエラーなしの場合もプロトコルエラーとして扱い、セッション情報は消費しない。status、reset、transmit、disconnect の各操作は、それぞれの呼び出し内で単一の制限時間を守り、失敗時はトランスポートを切断して要求の再送は行わない。リモートから返されたエラーコードは wire 上の値を忠実に保持する。CARD 操作の自動再試行は一切行わない。

## 独立 LNB 給電クライアント

`set_lnb_power(TimedClientTransport&, enabled, Timeout)` は、同一接続上で HELLO、LIST、STATUS を実行し、STATUS から得られた最新の epoch を使用して、opcode `0x0039` の `LnbPowerRequest` を要求 ID 4 で 1 回送信する。HELLO の開始から LNB 応答の受信まで単一のモノトニックタイマー（単調増加クロック）期限を共有し、処理途中で制限時間を延長しない。wire バージョンや機能ビットの追加は行わない。ハードウェアの LNB 給電能力、デーモン起動時の `--allow-lnb-power` オプションの有無、実機の物理的な給電制御はサーバ側の責任であり、本クライアントがそれらの権限や能力を代行することはない。

処理成功時は、応答電文の epoch および `enabled` フラグが要求内容と一致していることを確認した上で `LnbPowerResponse` を返し、接続を開いたまま復帰する。この応答電文は制御要求に対するサーバ側の受諾・処理結果を示すものであり、15V 端子の物理的な実測電圧や実機への給電成功を直接保証するものではない。リモートエラーの生コードはそのまま保持し、タイムアウト、EOF 検出、不正形式の電文、epoch や状態の不整合が発生した場合は、既定の空応答を返してトランスポートを切断する。要求の自動再送は行わない。制限時間値に 0 が指定された場合は `INVALID_ARGUMENT`、期限の算出値がモノトニックタイマーの uint64 範囲を超過した場合は `TIMEOUT` とし、いずれの場合も接続を切断する。

期限付き録画呼び出しにおいても、関数の戻り値、デコードされた型付きレコード、クライアント内部のスタックフレームは呼び出しスレッドのスタックを使用し、サイズ上限付きの送受信ワークスペースはヒープから割り当てる。Linux x86_64 環境における検証プローブでは、モックトランスポートおよび記録応答バッファをプローブスレッド外のヒープに配置し、GCC 14.2（Release）および Clang 19.1.7（Debug、ASan+UBSan 有効）の各 512 KiB スタック環境において、begin → stop → release の一連のシーケンスおよび期限付き status の早期 EOF 検出が正常に動作することを確認している。これは当該コンパイラおよびビルド構成での限定的な実測値であり、小規模スタック一般に対する動作を無条件に保証するものではない。呼び出し側は実際の実行スレッドに割り当てられたスタック予算、結果オブジェクトの配置場所、デコーダの内部処理、トランスポート実装の消費量を合算し、十分なスタック余裕を確保しなければならない。PID 要求処理用のスクラッチバッファは、上限付きヒープワークスペースを再利用して仕様上最大の正当な PID リストを処理する。これは読み取り専用要求で使用される小さな静的スクラッチ領域とは明確に区別される。
