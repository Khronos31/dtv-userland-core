## 1. 層モデル（採用済み）

利用者の層ごとに契約をひとつだけ割り当てる。上位の層は下位の層と同じ不変条件を同じコードで継承する。

| 層 | 対象 | 主な利用者 | 約束 |
|---|---|---|---|
| L1 プロセス | 引数（argv）、stdout への TS 出力、終了コード、シグナル・EOF、FD の受け渡し、runtime ディレクトリ | mirakc、dtv-android、各製品ランチャー | 1.0.0 の規範。メジャーバージョンで固定 |
| L2 wire と JSON | IPC レコード・opcode、discovery・status JSON | C# 実装などの外部クライアント、ctl | 規範。バージョンネゴシエーション付き（§4.5 の未決を含む） |
| L3 組込み | 製品間で共通シグネチャの C ヘッダー、各関数のセマンティクス（受付判定、ゲート、Error、所有権、取り消し・切断の期限） | WebTS.app、プロセス内組み込み利用者 | リリースごとに固定するソース契約。安定 ABI は約束しない |
| L4 内部 | Family、TunerServiceBackend、Core host アダプター、`detail/`、製品内部クラス | 製品自身のみ | 契約ではない。予告なく変更してよい |

- 層分けは採用済みである。L3 の構成は採用済みだが、個別 API の具体契約は設計対象であり、本採用だけで API を確定しない。
- L3 の約束は **リリースごとの固定** とする。リリースをまたぐ無期限の安定 ABI は新たに約束しない。
- L4 から L3 への昇格はユーザー判断とする。WebTS.app が現在使っている Family 等は L4 にあたる。
- `include/dtv/userland/detail/` は L4 の印として扱う。
- 目標構成（ユーザー 6603670549）: Core の共通ライブラリと、同じ共通仕様に適合する各製品ライブラリを持ち、実行バイナリはそれらと疎結合にする。入口だけを共通化してライブラリの責務・再利用性が整わない状態や、CLI 側が選局・ゲートを再実装する状態を完成としない。
- 契約テストは層ごとに作成し、どの層の規範を検査しているかを明記する。

## 2. 共通の前提

- 製品は 5 つである。公開コマンドは製品ごとにデーモン（`*d`）、通常 TS クライアント（`*-ts`）、制御ツール（`*ctl`）、および配布ランチャー/ラッパーで構成される。
- 通常 TS クライアントは **すべてデーモン IPC 経由** とする。torne の `--device` による直接 USB 経路は廃止し、共通のデーモン接続・物理デバイスのセレクタおよび検証アサーションとして扱う（採用済み）。
- 同じオプション名に製品ごとの別の意味を割り当てない。ハードウェアにない機能は黙って無視せず、明示的な未対応（unsupported）として返す。
- すべての入口が同じ規則に到達することを目的とする。同じコードを使うことはその手段のひとつにすぎない。

## 3. L1: プロセス契約

### 3.1 コマンドと役割

| 役割 | コマンド | 責務 |
|---|---|---|
| デーモン | `px4d` / `asicend` / `sianod` / `pixd` / `torned` | USB 筐体の所有権管理、ファームウェア転送、選局、キャプチャー、カード操作、IPC の公開 |
| TS クライアント | `px4-ts` / `asicen-ts` / `siano-ts` / `pix-ts` / `torne-ts` | デーモンへ接続し、選局・受信を行い、生の TS を stdout または `--output` へ書き出す |
| 制御ツール（ctl） | `px4ctl` / `asicenctl` / `sianoctl` / `pixctl` / `tornectl` | `list` / `status` / CARD / LNB など、ハードウェア能力に応じた制御と状態照会 |
| ランチャー | 各製品の配布ラッパー（実在: `px4-termux`、`asicen-termux`、`pix-termux`、`torne-termux`。Siano は未実装・共通化時に追加予定） | 権限・FD・runtime の準備、デーモン起動（またはワンショット実行）、終了時の後始末 |

デーモンは筐体ごとに 1 プロセスを基本とする。

なお、PIX はデーモン起動のほか、常駐させずに単発で選局・受信するワンショット（one-shot）実行の形態を持つが、他製品（PX4、ASICEN、Siano、torne）は常駐デーモンを起動して IPC 経由で受信する形態を基本とする。Siano のランチャー（`siano-termux`）は現時点では未実装であり、ランチャー共通化に合わせて追加予定である。

各コマンドの利用者が単独の表で対象オプションを確認できるよう、デーモン（`*d`）、通常 TS クライアント（`*-ts`）、制御ツール（`*ctl`）、Termux ランチャー（`*-termux`）の 4 つに分けて記載する。

- ランチャーの真の公開契約未決は、PIX 公開名/旧パスの互換性、および複数起動時の `--instance` 必須条件の 2 件である。

製品ごとの追加・除外オプションは各製品 SPEC の付録案に記載する。ここにないオプションを新設して同じ意味を持たせてはならない。

### 3.3 `--help` / `--version` / メタデータの優先

採用済みの規則:

1. `--help` および `--version` は、他の引数に構文エラーや不正があってもメタデータを表示して **正常終了（終了コード 0）** する。
2. `--help` と `--version` が同時に指定された場合は **`--help`** を優先して表示し正常終了する。
3. メタデータの解決は、通常引数の構文解析、デーモン接続、USB discovery、権限取得よりも前に行う。

`--models` / `--list-json` をヘルプやバージョンと同様の「単独要求」として優先するかは製品差があり、§7 の未決事項とする。

### 3.4 必須入力

- 全デーモン: `--firmware` による明示パスの指定が必須。
- 全 TS クライアント: `--receiver` による受信機インデックスの明示が必須。
- 通常 TS クライアント: `--channel` または `--freq` のいずれか一方が必須。
- `--freq` 指定時は `--system` が必須。`--channel` から system を一意に導出できる場合は省略可能。
- torne の通常ネイティブデーモン: `--device` を必須とし、最初の筐体を暗黙に選択しない。`--fd` を使用する場合およびメタデータ要求（ヘルプ/バージョン/models）では device を要求しない。models / ネイティブ device / Windows 限定 EOF / 外部ファームウェアは採用済みの対象であり、実装・検証の未完と混同しない（付録 E）。
- 明示必須の規則を、製品固有の既定値や「接続機器が 1 台なら省略可能」といった暗黙動作で置き換えてはならない。

### 3.5 短縮オプション名・重複・排他

- 維持する短縮名: `-h`、`-f`、`-c`、`-o`、`-t`、`-s`（採用済みのもの）。それ以外の短縮名は個別決定がない限り新設しない。
- 単一値オプションの重複指定は引数エラー（終了コード 2）とする。ロングオプションとショートオプションの混在重複も同様である。例: `--firmware FILE_A --firmware FILE_B`、`-f 1 --freq 2`。
- 複数指定が仕様上認められている入力（`--fd`、PID 等）は単一値オプションと区別する。重複判定は複数指定の仕様ルール内で行う。
- 相互排他規則: `--freq` と `--channel`、`--slot` と `--tsid`、`--time` と `--packet-count`（後者は条件付き）、地上波選局と `--slot`/`--tsid`。
- インスタンス名の大文字小文字は保持する。`RoomA` と `rooma` は別個のインスタンスとして識別する。旧草案にあった小文字正規化案を現在の規範へ再採用しない。

### 3.6 stdout / stderr

- TS 出力は生の TS パケットデータのみとする。`--output -` は stdout を表す。診断メッセージや進捗ログは stderr へ出力する。
- `--list-json` は単一の完全な JSON ドキュメントのみを stdout へ書き出す。前後に余計な説明文を混入させてはならない。
- ヘルプおよびバージョン表示は stdout へ出力する。
- 正常終了時のカウンター診断や失敗原因の詳細は stderr へ送る。stdout に混在させてはならない。
- `--models` はプレーンテキスト形式で出力する（JSON や CSV にしない）。

### 3.7 終了コード

共通分類 `0, 2..10, 70` を採用済みである。これらの数値を IPC のエラー enum と混同してはならない。

| 終了コード | 分類 | 主な対応状況 |
|---:|---|---|
| 0 | 正常終了 / 要求された停止 | 正常完了、時間上限やパケット数上限への到達、明示指定された stdin EOF、SIGINT/SIGTERM による通常のクリーンアップ完了 |
| 2 | 入力構文不正 | 引数構文エラー・範囲外・相互排他違反・単一値重複、`INVALID_ARGUMENT` |
| 3 | 対象/機能不在、状態不整合 | `NOT_FOUND` / `NOT_READY` / `UNSUPPORTED` / `INVALID_STATE`。曖昧な device 指定も 3 |
| 4 | 競合 | `BUSY`（別の所有者が使用中、資源回収中、同時ストリーム数制限超過） |
| 5 | 期限切れ | `TIMEOUT`（選局タイムアウト、IPC 応答待ち、停止回収タイムアウト） |
| 6 | プロトコル違反 | `VERSION_MISMATCH` / `PROTOCOL_ERROR`、破損フレーム、不整合な final レコード |
| 7 | USB 喪失 / 入出力異常 | `USB_IO` / `DISCONNECTED` |
| 8 | TS 継続不能 | `SLOW_CONSUMER`、バックエンドが終端エラーとして報告した TS 破損。単なるパケットドロップ増加は含めない |
| 9 | カード操作失敗 | `NO_CARD` / `CARD_REMOVED` / card API の `BUFFER_TOO_SMALL`。カード非対応製品でのカード要求は `UNSUPPORTED`→3 |
| 10 | 起動用データ不正 | `FIRMWARE_REJECTED`、必要なファームウェアやアセットの欠落・破損 |
| 70 | ローカル / 内部異常 | 出力オープン失敗・書込み失敗・EPIPE/ENOSPC、`ACCESS_DENIED`、`RESOURCE_LIMIT`、`INTERNAL`、未知の非 0 エラー |

- 動作中に最初に確定した回復不能エラーを主エラー（primary error）として固定する。利用者の要求による停止や少量のパケットドロップは主エラーを発生させない。
- 要求停止や time/packet 上限到達後であっても、それ以前に検出された USB 異常・出力異常・終端エラーを上書きして消去してはならない。
- 信頼できる正常な final レコードが取得できず、かつ STOP 処理によるハードウェアの停止（quiesce）が確認できない場合は成功（0）にしてはならない。
- 軽微なパケットドロップの発生のみを受信失敗とはみなさない。ドロップ発生後の正常終了は終了コード 0 とする。
- 個別の Error から終了コードへの細部対応は採用済み記録・実装と照合し、本書の表を新規の数値決定として扱わない（§7）。

### 3.8 シグナルと stdin EOF

- SIGINT/SIGTERM による終了は、通常の手順で資源クリーンアップを完了した上で終了コード 0 とする。クリーンアップ自体が失敗した場合は該当する終了コード分類に従う。
- `--exit-on-stdin-eof` は **Windows 限定** のオプトイン（明示指定）機能であり、既定はオフとする。指定時は stdin パイプの EOF 検出から通常のクリーンアップへ移行する。POSIX 環境では現行どおり未知引数エラー（終了コード 2）を維持し、Core の共通設計を理由に全 OS 対応へ独自に変更しない。
- 全体の終了処理において、制限時間内にハードウェアの停止（quiesce）が完了しない場合は異常終了とする。秒数および OS プリミティブの選定は実装・試験事項とする。

### 3.9 channel と周波数

- `--freq` は符号なし 10 進数による Hz 表現（1..2^53−1、JSON 整数表現との共通上限）。入力された Hz 値をそのまま保持し、バックエンドだけが必要な周波数単位へ量子化する。断りなく別の周波数へ丸めてはならない。
- `--channel` は mirakc などの設定（`--channel {{channel}}`）からそのまま渡せる文字列。共通で受理する形式:
  - 地上波: `13`..`62`、`T13`..`T62`
  - BS: 奇数 `BS01`..`BS23`、任意で `_0`..`_11`（ゼロ埋めなし）
  - CS: 偶数 `CS2`..`CS24`（`CS02`..`CS08` も受理）
  - 地上波チャネルは自動選択とし、slot/TSID の併記を拒否する。接尾辞なし BS は slot または TSID の明示が必須。接尾辞あり BS は接尾辞で指定された slot を使用し、追加の slot/TSID 併記を拒否する。CS は既定 slot 0 とし、明示された slot/TSID があればそれを優先する。衛星の直接周波数指定では明示的な slot または TSID が必須。slot は 0..11、TSID は 1..65534。
- system は `isdb-t` / `isdb-s` の ASCII 文字列（大文字小文字を区別しない）。channel と併記する場合は両者が一致しているときのみ受理する。
- 引数パーサーが受理可能な入力範囲と、接続機器のハードウェア能力を明確に分離する。未対応の帯域・変調方式・slot は USB 操作を行う前に `UNSUPPORTED`（終了コード 3）として早期に拒否する。

## 4. L2: wire と JSON

L2 の規範は Core の各個別文書に置く。本書はシステム全体の入口および横断規則をまとめるにとどめ、全レコードの個別フィールドを複製しない。

- エンベロープ・フレーム・HELLO/ACQUIRE の先頭サブセット: [`wire-subset.md`](wire-subset.md)
- 型付きレコードと STATUS/LIST: [`wire-records.md`](wire-records.md)
- 接続ゲート: [`control-connection.md`](control-connection.md)
- 認可制御 (Authority) / セッション: [`control-authority.md`](control-authority.md)
- 読み取り専用 / 録画クライアント: [`control-client.md`](control-client.md)
- ストリームのライフサイクル: [`receiver-v1-stream.md`](receiver-v1-stream.md)
- discovery JSON: [`json-discovery.md`](json-discovery.md)
- status JSON: [`json-status.md`](json-status.md)

### 4.1 転送方式とエンドポイント

- POSIX/Android 環境では Unix ドメインソケットを使用する。Windows 環境では名前付きパイプおよび適切な ACL を使用する（Core の host runtime が差異を吸収）。
- エンドポイントのパス構造は `<runtime>/<product-slug>/v1/<instance>/<endpoint>`。`endpoint` は `control.sock` または `stream.sock`。product slug は `px4-userland` 等。
- 接続の所有権は呼び出し側にある。Core ライブラリ自体はソケットを生成しない（host runtime がアダプターとして提供）。
- エンドポイントの所有者/アクセス権・ピア UID（POSIX）、所有者 SID・保護された DACL（Windows）を厳格に検証する。共有グループ設定は POSIX のみ有効。

### 4.2 エンベロープ

- magic は ASCII `UDTV`。旧方式の `PX4U` および `ASCN` は拒否し、そのペイロードは一切解釈しない。
- 20 バイト固定ヘッダー。すべての整数フィールドはリトルエンディアンで配置する。
- major=1、minor=0。それ以外のバージョンは `VERSION_MISMATCH` とする。
- opcode は raw u16。未知の opcode であってもエンベロープ形式としては受理し、ディスパッチャーが `UNSUPPORTED` を返す。
- flags は 0、1、3 のみ受理する。それ以外の値は不正形式とする。
- 通信種別（kind）の正当な組み合わせ:
  - 要求（request）: opcode bit15=0、flags=0、request_id≠0
  - 応答（response）: opcode bit15=0、flags=1、request_id≠0
  - エラー応答（error_response）: opcode bit15=0、flags=3、request_id≠0
  - イベント（event）: opcode bit15=1、flags=0、request_id=0
  - それ以外のすべての組み合わせはプロトコル違反（`PROTOCOL_ERROR`）とする。
- `payload_length` はペイロードの読込みを開始する前に上限値と照合して検査する。
- ペイロード上限: TS_DATA イベントは 1,048,504 バイト（1,048,476 + 28）。その他のフレームは 65,536 バイト。
- `FrameReceiver` は断片化・連結フレームを適切に再構成する。未完了フレームは 5 秒で破棄する（OS アダプターが制限時間を強制）。フレームの途中で EOF に達した場合は `PROTOCOL_ERROR` とし、再同期・再接続は行わない。

### 4.3 接続状態と遷移

- 制御接続における最初のフレームは必ず HELLO とする。HELLO によりバージョンと機能（feature）をネゴシエーションする。一方、データ接続は ATTACH_STREAM から開始する。
- 1 つの接続内で同時に処理できる要求は 1 件のみとする。request_id は単調増加させ、再利用や過去の ID の再使用を拒否する。
- 応答は、opcode および request_id が一致する response または error_response のみを受理する。
- 正常な状態遷移順序: HELLO/LIST/STATUS を経て、ACQUIRE→TUNE→START→ATTACH→TS_DATA→STOP→RELEASE の順に進む。
- epoch は同一リリース内での接続識別子である。LIST と STATUS の epoch が一致していることを照合する。
- 制御接続とデータ接続を分離する。ATTACH と TS_DATA はデータ接続で扱い、制御接続は要求/応答のみを運ぶ。
- ネゴシエーションで不足している機能は `UNSUPPORTED` とする。未知の機能ビットはそのまま透過（パススルー）し、コーデックレベルでは判定しない。

### 4.4 ペイロード形式

- 型付きペイロードは、各レコード定義で定められた過不足のない正確なサイズを要求する。サイズ不一致は `PROTOCOL_ERROR`、サイズが合致していても意味的な値が範囲外であれば `INVALID_ARGUMENT` とする。
- 文字列は `u16 length + UTF-8 バイト列`、可変バイト列は `u32 length + バイト列`、配列は `u16 count + 要素列`。要素数上限はレコードごとに規定する。
- 整数は固定幅リトルエンディアンでエンコードする。JSON での 64 ビット整数の扱いは一律に文字列化せず、フィールドごとの契約に従う。`frequency_hz` および `programmed_hz` は数値（上限 2^53−1）として保持し、`sequence`、`observed_at_ns`、`stream id`、`revision`（epoch の 16 進表記を除く）等は 10 進文字列として表現する。
- Model は wire および JSON ともに **名前のみ（name-only）** とする（`str[128]` / 文字列または null）。モデル ID は出力しない。
- リース、ストリーム、カードハンドル、世代番号（generation）の各 ID は 0 以外（nonzero）とする。カウンタの飽和規則として、`overflow=true` の場合は `value == UINT64_MAX` を要求する。
- `frequency_hz` および指定時の `programmed_hz` は正数かつ最大 2^53−1 とする。プロファイル範囲の検査はコーデックの外側で行う。
- STATUS の筐体（enclosure）観測値（`lnb_15v_enabled` / `card_inserted`）は「未観測・不明」と「観測された false」を厳格に区別する。`card_inserted` は筐体内部での観測値であり、外部リーダーの集計値ではない。
- 未知の任意カウンタは完全に検証した上で JSON 変換（マッピング）ではスキップし、既知のフィールド名の別名（エイリアス）として割り当てない。

### 4.5 バージョン管理と互換性

- エンベロープバージョンは UDTV 1.0 とする。HELLO の min/max 範囲で 1.0 を選択し、合致しない場合は `VERSION_MISMATCH` とする。
- **L2 は外部契約として採用済みである。** 層モデルの採用に伴い、wire のレコード構造・opcode および discovery/status JSON は外部クライアントや ctl を含む第三者向けの境界であり、バージョンネゴシエーション付きの規範とする。外部契約化そのものを未決に戻してはならない。
- Core の既存ドキュメント（`control-client.md` / `control-connection.md`）にあった「同一リリース内の内部契約であり、リリースをまたぐ安定 wire API ではない」という記述は、仕様草案化以前の古い位置付けである。本 1.0.0 外部契約と整合するよう各文書を改稿する。
- **スコープを限定した未決事項:** リリースをまたぐ具体的な互換性範囲。同一メジャー内で許容する差分（レイアウト変更・機能ビット・マイナーバージョンの扱い）と、同一リリース前提を残す範囲を決定する。推奨方針は「マイナーバージョンは機能ビットでゲートし、レイアウト変更は明示的な機能ビットまたはバージョン引き上げで区別する。L3 と同様に永続的な安定 ABI は約束しない」。
- レイアウト変更を機能ビットでゲートするか、同一リリース前提の非互換変更として扱うかは、上記のスコープを限定した未決事項に含める。

### 4.6 リソースの所有権・取り消し・切断

- ACQUIRE は利用権（リース）を発行する。リースは接続が切断された際にデーモンによって回収される。
- START は選局リビジョンとアタッチ用トークンを発行する。トークンはデータ接続の ATTACH にのみ使用する。
- **wire の STOP 応答は `epoch`、`final`、`quiesced` を返す。** 停止処理の最終結果とハードウェアの静止状態（quiesce: 動作が完全に停止したか）を外部クライアントに示す。物理的なクリーンアップの実行責任および所有者の割り当てはデーモン内部（エンジン/ワーカー）の契約であり、wire のフィールドではない。`cleanup_owner` や `complete_stream_cleanup_v1()` は内部実装の説明であって、外部クライアントが直接読み取る値ではない。
- `quiesced=false` はハードウェアの停止処理が未完了（未静止状態）であることを表す。final レコードを受信したことのみをもって、ハードウェアが完全に停止（quiesce）したとみなしてはならない。
- 停止処理および接続切断処理は有限の期限を持つ。完了が未確定のまま放置された要求を成功として扱ってはならない。全体切断の秒数は候補値であり、実機認定値ではない。
- エラーが付与された final レコードは共通分類に従う。要求された停止に結び付かない `owner_closed` や `CANCELLED` は終了コード 70 とする。
- パケットドロップは計数するが、それ単体を受信失敗とはみなさない。

### 4.7 エラー体系

- error_response は 0 以外のコードおよび詳細情報を持つ。コードは Core の `Error` enum の定義に従う。
- Core enum の範囲外のエラーコードは、JSON では `code: "UNKNOWN"` と元の数値 `numeric_code` を出力する。
- すべての入口から同一のエラー分類へ到達することを目標とする。アダプター層が BUSY、NOT_FOUND、ACCESS などの区別を潰してはならない。
- wire における具体的なエラーペイロード（`Error`）のバイト配置については、[`wire-records.md`](wire-records.md) において検証分離規則および 0 以外のコードを要求する確定規則が示されているものの、全フィールド順や各幅を確定できる完全なレイアウト表は未記載である。公開済みの規範範囲と未記載の境界を明確にし、欠落を推測や旧利用者実装で補ってはならない。

### 4.8 JSON

公開される JSON は以下の 2 種類である。

- `userland.discovery`: 機器スキャン結果。`schema`、`producer`、`scan`、`enclosures`、`ungrouped_usb_devices`。物理階層 `enclosures[].devices[].receivers[]` を保持する。ID は JSON の数値、VID:PID は小文字の `VID:PID` 文字列とする。
- `userland.status`: 検証済み `StatusResponse` のマッピング（JSON 変換）。`schema`、`producer`、`context`、`snapshot`、`scope`、`enclosure`、`topology`、および存在するコレクションのみを出力する。

横断規則:

- 64 ビット整数は一律に文字列化せず、フィールドごとの契約に従う。`frequency_hz` や `programmed_hz` は数値（上限 2^53−1）として保持し、`sequence`、`observed_at_ns`、`stream id`、`revision`（epoch の 16 進表記を除く）等は 10 進文字列として表現する。
- 欠測値・不明値は JSON `null` とする。観測された false とは厳密に区別する。
- 列挙値は独自の語彙を作らず、定義済みの識別文字列（リテラル: `ready`、`ISDB-T`、`isdb-t` 等）を使用する。
- `model` はモデル名のみを出力し、内部 ID は出力しない。
- 識別子のスコープ（有効期間 / ライフタイム）: epoch は同一リリースの接続識別子、function/receiver/reader ID はスナップショット内、lease/stream/card handle は操作単位とする。スキャンのインデックスを永続識別子として転用してはならない。
- 出力処理は「検証 → 事前サイズ計測 → 書込み」の順序を守る。失敗時に出力バッファを変更してはならない。文字列は JSON のエスケープ規則に従い、有効な UTF-8 を維持する。
- 1 回の出力は 1 つの完結した JSON ドキュメントとする。末尾改行の有無は各既存 API の契約に従う。

## 5. runtime ディレクトリとファイル記述子の受け渡し

### 5.1 runtime ディレクトリ

- `--runtime-dir` は全製品で提供する。明示された値が不正な場合は、暗黙のフォールバックを行わず即座にエラーとする。
- 引数が省略された場合は、Core resolver による共通解決方式を採用する（POSIX/Windows/Android の全製品で統一。現在別 PR で実装・各 OS の実機検証中）。POSIX 環境で `--group` を指定する場合は、明示的な `--runtime-dir` の指定が必須である（省略時は引数エラー 2 とし、自動解決による private root を group 共有に流用してはならない）。
- 解決規則（Core host runtime）:
  - POSIX: 絶対パスの `$XDG_RUNTIME_DIR` → `$TMPDIR/dtv-userland-<euid>` → `/tmp/dtv-userland-<euid>`。相対パス、空文字、長すぎるパス、ドットコンポーネントは除外する。
  - 省略時の自動解決（自動候補の導出）においては、祖先信頼チェーンを厳格に検証する（全祖先が信頼主体である root または euid の所有であり、非信頼主体からの書き込み権限がないこと。sticky ディレクトリ内のエントリ自体が信頼主体所有であること。非 sticky 共有祖先は拒否する）。一方、利用者が明示指定した `--runtime-dir`（明示 root）は利用者が選択した信頼境界であり、この自動候補向けの祖先検査規則を一律に強制して既存の利用可能なパスを拒否することはない。
  - Android（Termux）: `__ANDROID__` では信頼主体を root・euid・AID_SYSTEM（uid/gid 1000）とし、グループ書き込みは gid 1000 と自身の per-app gid のみ許容する。
  - Windows: `%LOCALAPPDATA%` 配下のみとし、自動フォールバックは行わない。所有者 SID および DACL を検証する。
- エンドポイントの配置は `<runtime>/<product>/v1/<instance>/<endpoint>`。インスタンス名の大文字小文字は保持する。
- デーモンは runtime 配下の自身が必要とする階層のみを作成する。呼び出し側が root を事前に準備する契約の製品では、その境界を付録に明記する。

### 5.2 ファイル記述子（FD）

- `--fd` は POSIX/Android におけるデーモン起動用の USB デバイスのファイルディスクリプタ（FD）である。TS 出力先の FD や PID とは明確に区別する。
- 10 進数表記の 3..INT_MAX を受け付ける。符号付き、空白混入、16 進数、8 進数解釈、位置引数による FD 指定は廃止とする。`03` は数値 3 として扱い、8 進数解釈を行ってはならない。
- 複数指定が可能。同一数値の重複指定は引数エラー（終了コード 2）。最大上限は 8（wire 仕様のファンクション上限）。
- 渡された FD の集合が開くべき対象を完全に限定する。USB 名前空間を独自に再列挙して不足しているファンクションを開いてはならない。`--device serial:...` や `usb:...` は渡された FD 集合に対するアサーション（確認検証）としてのみ使用する。
- デバイス不一致、別筐体の混在、同一ファンクションの複数 FD での二重指定は終了コード 3。クローズ済み FD や USB でない FD は終了コード 2。FD の検査 I/O 失敗は終了コード 7 とする。
- 引数の指定順序を受信機番号やファンクション番号と同一視してはならない。USB の記述子メタデータおよびプロファイルに基づいて役割を照合する。
- ドライバーは内部で FD の複製（dup）を作成し、CLOEXEC フラグを付与して保持する。クローズや解放はその複製に対してのみ行う。部分的な失敗時は作成済みの複製を回収し、呼び出し側から渡された元 FD をクローズしてはならない。
- 元 FD の所有権はホスト側にある。ホストはコンテキストの `quiesced=true`（ハードウェアの停止処理完了）による完了、または USB FD を保持しうる全プロセスの終了・回収確認まで、呼び出し元の元 FD をクローズしてはならない。
- Windows 環境では数値の POSIX FD を HANDLE へキャストせず、未対応（`UNSUPPORTED`、終了コード 3）とする。
- コールド状態からウォーム状態へのファームウェア再列挙により、FD が自動的に新デバイスの FD に切り替わることはない。必要な権限および新 FD はホスト側からの明示的な引き渡しを必要とする。

### 5.3 インスタンスと識別子

- インスタンス名は各製品デーモンの多重起動を識別するための名前空間である。
- 同一マシン上で同一製品の複数インスタンスが競合なく独立して動作できるよう、runtime パスおよびソケット名にインスタンス名を組み込む。
- デーモン起動時にインスタンス名が重複し、かつ既存インスタンスがアクティブである場合は、競合エラー（`BUSY`、終了コード 4）として起動を拒否する。

## 6. L3: 組込み（インプロセス）契約（設計案）

### 6.1 採用済みの構成

- **案 C の構成を採用済みとする。** 共通 C インタフェース（C API）、`submit`/`completion`/`cancel` による非同期 USB コア、ワーカースレッド上の同期ブリッジを採用する。
- Core の共通ライブラリと、共通仕様に適合する各製品ライブラリを分離し、実行バイナリと疎結合にする（ユーザー 6603670549 の方針）。
- L3 の契約は **リリースごとのソース契約** とする。リリースをまたぐ無期限の安定 ABI は約束しない。
- 呼び出し側が USB デバイスの所有権およびイベントループを保持し、ライブラリ側へ借用させる。
- 個別の関数名、シンボル名、型、ABI、構造体レイアウト、エラーコード数値は未決であり、確定事項として扱わない。

### 6.2 設計案の要約（採用済みの構成: 共通 C API＋非同期 USB コア）

設計案では 3 案を比較し、案 C を採用した。以下の詳細は設計案であり、個別 API は未決である。

- **案 A**: 既存の `Family` / バックエンドに薄い C ラッパーを被せる。5 製品の I/O・所有権・選局順序が揃わず、GPL-2.0-only のアダプターに依存する。
- **案 B**: 共通 C API ＋ 同期 USB コールバックのみ。特定の同期型利用者には近いが、連続 TS 受信やブラウザー環境での取り消し・有限停止を共通規則にしにくい。
- **案 C（採用）**: 共通 C API ＋ `submit`/`completion`/`cancel` による非同期 USB コア。同期コールバックはワーカー上の同期ブリッジで接続する。呼び出し側の USB 所有権と WebTS.app などのイベントループ非ブロッキング性を両立し、libusb/WebUSB/WinUSB の管理責任をホスト側に残す。

責務の分離:

| 構成要素 | 責務 | 含まれない責務 |
|---|---|---|
| Core L3 契約ヘッダー（MIT 提案） | 共通型、Error、リリース照合、受付/完了/取り消し、所有権・状態、能力照会の語彙定義 | USB 列挙、デーモン管理、OS ソケット、カード復号器、製品固有の選局手順 |
| Core 共通ロジック層（MIT 候補） | チャネル/周波数解決、受付判定、lease/revision/stream 世代管理と結果セマンティクス | 未整理の内部エンジンの流用、内部クラスの公開 |
| 製品 L3 アダプター | 型変換、能力と実機観測、ファームウェア検証、電源/選局/ロック/取得ゲート、TS 処理、カード/LNB 制御、切断時の影響局所化 | 呼出側 UI、OS 権限取得、デーモン管理 |
| 呼出側 USB プロバイダー | 認可済みデバイストークンの列挙、記述子取得、open/claim/release、control/bulk/interrupt の submit/completion/cancel、モノトニックタイマー（単調増加クロック） | 選局・ファームウェア適否判定。認可されていない USB 要求の隠蔽 |
| ホスト実行基盤 / 同期ブリッジ | 製品処理をワーカースレッドで実行し、同期 I/O を前提とする呼出しを submit/completion へ変換 | UI/メインスレッドの同期待機、ワーカースレッドの無制限な生成 |
| L1/L2 アダプター | 同じ製品 L3 セマンティクスを CLI/wire へマッピングし、runtime ディレクトリ、引数、認証、FD 受け渡しを管理 | L3 と異なる選局順序やファームウェア検証の再実装 |

データの流れ（設計案）: ホストが認可済み USB トークン/記述子をプロバイダーへ登録 → `catalog`（静的）または `discover`（登録済みトークンのみを観測、claim しない）→ 明示候補で `open` → アダプターが同一デバイスを再照合し、必要なファンクションを claim し、ファームウェアを検証して初期化 → `acquire` → `tune` が給電トランザクション、slot/TSID の前後順、ロック/セトル、取得ゲートを単一の期限内で実行 → `start`/`attach` で TS プレーンを有効化 → `read` で 188 バイトのパケットを受け渡し → `stop`/`release`/`close` で完了回収。

API の形状（**名称・採番・構造体レイアウトはすべて未決**。以下は設計案であり、個別 API の採用ではない）:

- 製品ごとに同じ `dtv_l3_api` を返すファクトリー（例: `px4_l3_get_api_rX`）。複数製品の静的リンク時にシンボルを衝突させず、異なるリリースのヘッダー/実装を混在させた場合はリンク時またはパッケージ照合時に明示的に失敗させる。
- `release_id`、`catalog`、`discover`、`submit_open`、`capabilities`、`acquire`、`submit_tune`、`submit_start`、`submit_attach`、`read`、`submit_stop`、`submit_release`、`submit_close`、`close_status`、`context_release`、`poll`、`cancel`、`op_release`、CARD 系、LNB 系。`close_status` と `context_release` は設計案の名称であり、採用済み API ではない。
- `dtv_l3_result`（要求の即時受付結果）と `dtv_l3_completion`（操作の終端結果）を明確に分離する。`submit_*` の成功は受付のみを示す。`poll` の `PENDING` は未完了を示す。終端結果 `TIMEOUT` は期限超過を示す。受付のみから物理完了や USB の完全停止（quiesce）を推定してはならない。
- 完了通知は操作種別のタグ付き共用体（union）。open→成功・失敗を問わず所有者 context、tune→`{revision, requested_hz, programmed_hz?, verification, lock_measurement}`、start→armed stream、attach→active stream、card reset→ATR、APDU→応答バイト列、close→`{quiesced, retained_scope}`。受付前の検証失敗は副作用なしで op/context を生成しない。一度受理した open は、部分的な claim や I/O を残す失敗であっても回収可能な context を返し、ホスト側が close および最終解放を行う。
- `op_release` は終端完了の取得後にのみ許可される。解放対象は操作結果および op ハンドルであり、内部 I/O 参照・context・プロバイダー・バッファの最終解放とは別である。結果バッファとハンドルは取得側が明示的に解放する。
- `read` は `DATA(n)` / `WAIT` / `EOF` / `TERMINAL(error)` を別タグで返す。バッファは呼び出し中のみ借用され、内部保持されない。`drop_total_packets`（キューで正確に破棄された数）と `upstream_loss_unknown`（USB/復元段で個数不明の欠落）を区別し、前者の増加のみでストリームを失敗とはみなさない。
- 状態: context `opening/ready/closing/closed/failed/disconnected`、receiver `free/leased/tuned/streaming/error`、stream `none/armed/attaching/active/closing/ended`、card `closed/open/reset/transaction/closed`。所有者ハンドルは context 世代を持ち、閉鎖後の旧ハンドルを古いものとして拒否する。
- `tune` は system、`uint64_t` Hz、`auto|slot|tsid` の一択、LNB 電圧/許可、有限の期限を持つ。チャネル文字列の解決は Core の純粋関数で 1 回行い、要求 Hz と実際に設定した Hz を分ける。ロックを測定できない製品に架空の true を生成しない。
- ファームウェアの供給元は `path`、呼出側 `bytes`、上限付き `read(offset, buffer)` コールバックの排他的な三形。三形ともライブラリ管理領域へコピーしてから検証・USB 書込みへ進む。各製品の manifest/format/model/SHA-256 を USB 書込み前に検証し、呼出側の自己申告ハッシュだけで任意の image を承認しない。cold で必要なら `FIRMWARE_REJECTED`、warm で不要なら無転送。L1 のデーモン `--firmware` 明示必須は維持する。
- プロバイダーはホスト所有。`submit` は受付のみ、転送には正常/失敗/取り消しを問わず一つの最終完了を返す。`cancel` 成功は取り消し要求の受付であり、バッファ解放の許可ではない。timeout・部分転送の副作用は不明な場合があり、自動再送は行わない。ライブラリは別の libusb イベント所有者を起こさない。
- `close` は新規受付停止→全 op/stream のキャンセル要求→コールバック回収→card/receiver/USB claim 解放、の有限のエンドツーエンド期限。ここで **操作の期限結果** と **資源の最終静定** を別に観測する。期限内に静定したときだけ `quiesced=true`。期限切れの close op は `TIMEOUT/quiesced=false` と未解放 scope を返して終結し、ホストはその op を release できるが、context・プロバイダー・バッファ・元 FD/USBDevice と内部 I/O 参照は保持する。既に close 中の context への重複 `submit_close` は新しい停止/release を行わず既存の closing 状態を返す。
- `close_status` は同じ所有者ハンドルで非ブロッキングに再照会し、`{phase, quiesced, retained_scope, cleanup_error}` のスナップショットを返す。`quiesced=true` は全受理済み I/O の最終完了回収と card/receiver/claim の後始末が終わったときだけ単調に成立する。保持中の scope がなければ `context_release` を一回だけ許す。`context_release` は静定前なら拒否し、成功後のポインターは無効になる。内部は一回限りの release 遷移で二重コールバック/二重解放を防ぐ。
- 進行担当を分ける。driver 実行レーンは製品の同期手順で待機し得る。USB 完了/イベントポンプ、キャンセル受付、期限通知、`close_status` の読み出しを、その占有レーンに積まない。driver と独立したイベントポンプが最終完了を進め、control/期限担当が `TIMEOUT/quiesced=false` を公開する。クリーンアップは最終転送完了後に進み、完了後だけ `quiesced=true` へ遷移する。専用スレッドを一律必須にしない。
- 例: 受理した open が claim 後に失敗しても、終結果の所有者 context で close を依頼する。クローズ期限中に同期プロバイダーが戻らなければ control/期限担当が `TIMEOUT/quiesced=false` を返し、main は join せず応答を続ける。ホストが close op を release しても資源は残る。遅延した USB の最終完了と driver 復帰の後にクリーンアップが一回完了し、`close_status` が初めて `quiesced=true` を返す。ホストは全 op ハンドルを回収したうえで `context_release` を一回だけ実行し、プロバイダーと元 device/FD を解放できる。遅延完了だけで後始末が終わらない場合、またはプロバイダーが最終完了を失った場合は静定を偽らず保持を続ける。
- 旧 context を閉じず同じ token/FD を新 context へ再貸出ししない。USB 断は関係する function の generation を無効にし、依存する receiver/card を終端状態にする。再接続は新 token/新 context で明示的に行い、旧ハンドルを復活させない。
- リリース固定: 各製品リリースのヘッダー、ソースマニフェスト、Core pin、製品アダプターの組を固定する。ビルド/パッケージ時に照合し、製品名・リリース識別付きファクトリーで異版の静的リンクを失敗させる。`release_id` は一致した組の診断表示であり、異なるリリースのバイナリとの安全な runtime 交渉には使わない。
- 検証は**提案であり未実行**: 疑似 IO で L1/L2/L3 の受付判定が同じ不正値をハードウェアへ一度も届けないこと、遅延完了後のバッファ保持、キャンセル受付と静定完了の分離、各製品の非対応機能と共有資源の BUSY、TS drop と終端。WASM リンク/ブラウザーと P/Invoke 利用者、対象 OS の USB・受信品質は別の実装後検証。

### 6.3 利用者から出ている要件（参考であり、採用決定ではない）

利用者から出ている要件は、正本ではなく設計の参考として扱う。個々の関数名・数値・エラー enum を自動採用しない。次は現案との対応状況であり、未対応を採用済みと書かない。

- WebTS.app: PX4 のみを現在使用。Family ではなく部品を自前で組み立てている。非同期の submit/completion/cancel を基本にしたいが、ワーカー上の同期ファサードでも受け入れる。main とワーカーの相互待ちを作らないこと、バッファを借りる期間、キャンセル後に遅れて来る完了、クローズ期限切れ時の資源扱いを明記してほしい。内部でスレッドを作ることは要求しない。card+B25 と PIX の機器内復元を同じ API に押し込まないでほしい。
- in-process 利用者: プロセス内での利用を希望。USB 転送は呼び出し側が渡す形を想定し、ライブラリは libusb を必須にしないことを希望する。P/Invoke から呼べる C 面を求め、安定 ABI は要求しない。Siano と PX4 を同一バイナリへ静的リンクし、外部 symbol を衝突させないこと、共通の型・関数表を持つことを希望する。同期の読み書きで足り、連続 IN は出しっぱなしの読みで扱うことを想定する。スレッドを作らないことを希望し、必要なら数と停止方法の明示を求める。
- 既存の Family/`EnclosureFamily` は GPL-2.0-only のアダプターに依存するため、全利用者の共通境界にはできない。L3 は新しい C 面とリンク境界を分ける設計を採る。
